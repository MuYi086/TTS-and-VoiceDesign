# 空间音频未完成功能

> 更新日期：2026-08-24  
> 判定依据：《空间音频技术方案查询》的 Phase 0–6 与 Definition of Done，并与当前 `TTS-and-VoiceDesign`、`TTS-Studio-WebUI` 实现逐项对照。

本文只记录尚未完成或尚未真实验收的内容。“已写代码但缺真实环境验收”与“功能尚未实现”分开标注，避免把验收缺口误当成代码缺失。

## 本次复核结论

结论是：**没有全部完成**。2026-08-24 已用本机 Steam Audio SDK 4.8.1 重新构建当前源码，
CMake/CTest 全部通过；真实 CLI 使用内置 HRTF 输出了 48 kHz 双声道 WAV。随后实际启动 8300，
用 `fireRedTTS3.wav` 分别完成 balanced WAV 与 immersive MP3 请求，响应均为 200；WAV 为
48 kHz、双声道、24-bit，MP3 为 48 kHz、双声道、192 kbps，`GET /v1/control` 的 renderer、
SDK header/library 和 HRTF 可用性也全部为 true。因此原文“本机未配置 SDK/CMake”和“只做了
mock renderer”已不再准确。

本次同时补齐了长任务可观测性：WebUI 为正式导出提交唯一 `job_id`，轮询
`GET /v1/audio/spatial/render/progress/{job_id}`，显示后端阶段、0–100 百分比和进度条；8300
终端按同一 job ID 输出请求校验、资产暂存、逐对象标准化、renderer 逐对象进度、母带、完成或失败。
状态接口和终端链路已用真实 renderer 验证。

2026-08-24 进一步修复了 1× 倍速对象在 FFmpeg 6.1.1 中使用
`atempo=1,aresample=...:resampler=soxr` 时可能停在 EOF 的问题：1× 对象现在直接跳过无操作的
`atempo`，非 1× 对象仍保留变速。逐对象标准化进度在首个对象完成后显示 ETA，并在结束时报告
总耗时。本机用 3.52 秒、24 kHz 单声道输入串行标准化 98 个对象耗时 3.471 秒，平均
35.4 ms/对象，因此没有为该阶段引入 GPU 或额外并发；renderer 自身的并行度仍是下文单独记录的
未完成功能。

仍未完成的主要范围是 Windows 目标机、六方向/距离/移动与资源释放故障注入验收、固定音频指标和
盲听基线、真实浏览器完整工作流、renderer 并行度、增益包络、服务端取消、容量定标、LLM 固定
评测集，以及 Phase 5/6 和 Diffuse/Ambisonics。下面逐项保留这些缺口。

## 二、首版代码仍存在的功能缺口

### 1. Renderer 并行度未生效

`STEAM_AUDIO_RENDER_THREADS` 和 CLI `--threads` 已可配置，但 `render_manifest()` 当前仍按 `manifest.sources` 逐个串行渲染，`RenderOptions.threads` 没有参与任务调度。需要二选一：

- [ ] 实现有界并行渲染，并保证混音顺序、Steam Audio 对象生命周期、内存峰值和输出确定性；或
- [ ] 在未实现并行前去掉对外线程参数，避免运维误以为调整它会提速。

### 2. 正式 Manifest 没有增益包络

当前每个对象只有恒定 `gain_db`，没有 fade-in/fade-out 或通用增益包络。因此旧 Web Audio 链路中的 SFX 短淡入/淡出和 BGM 结尾淡出不会被编译进正式 Steam Manifest，可能出现突然起停。

- [ ] 为 Manifest 增加受限、可验证的增益包络表达，或在 FFmpeg 对象预处理阶段确定性烘焙包络。
- [ ] 补充 BGM play/stop、未显式 stop 的尾部淡出、SFX 四种 `mix_preset` 的包络回归测试。

### 3. 客户端断开不会取消后端渲染

当前 WebUI 的 Abort 只停止浏览器等待；后端依靠自身超时、成功或失败路径回收进程和临时文件。

- [ ] 如产品需要“点击取消即终止渲染”，需增加服务端任务 ID/取消协议，或可靠的客户端断开检测。
- [ ] 补充真实长运行子进程下的客户端断开、取消、超时和响应完成清理测试。

### 4. 长时间与大工程性能未定标

- [ ] 对 30 秒、5 分钟、20 分钟三档工程记录端到端耗时、峰值 RAM、临时磁盘占用和源数量扩展曲线。
- [ ] 确认 500 源、2 小时等契约上限是可运行的容量边界，而不只是 schema 校验数字。
- [ ] 根据实测决定源并行数、FFmpeg 并发数和临时空间预留策略。

## 三、LLM SpatialDirector 尚未完成的质量验收

空间 DSL Prompt、严格 JSON 解析、确定性规则回退和手动编辑已接入，但还缺真实模型评测：

- [ ] 用本地 Qwen 和云端 OpenAI 兼容接口分别验证同一 Schema，并保留脱敏的输入/输出用例。
- [ ] 建立固定评测集，量化同一角色跨句位置稳定性、无线索时不过度空间化、身后/楼上/远近/移动识别和非法 JSON 回退。
- [ ] 验证首版不支持的“门后”等语义不会被静默伪装成已有物理遮挡；当前 Prompt 已强制 `occlusion: none`，但仍需真实模型回归。
- [ ] 增加 Prompt/Parser 的专项自动测试，覆盖 Markdown 代码块、额外解释、枚举越界、缺字段、截断 JSON 和超长响应。

## 四、明确属于后续阶段的未实现能力

### Phase 5：Reflections / Reverb

Manifest 已接受 `scene.room` 预设标签，但 C++ renderer 目前忽略该标签；`bedroom`、`narrow_corridor` 等值不会产生任何声学差异。

- [ ] 房间几何 preset：`bedroom`、`narrow_corridor`、`stairwell`、`basement`、`warehouse`、`cave`、`outdoor_open`。
- [ ] 材质定义与 Steam Audio Scene 构建。
- [ ] 早期反射、后期混响和合理尾部时长。
- [ ] `acoustic_quality` 到射线数、反射阶数、尾部长度的受限映射。
- [ ] 同房间场景缓存，必要时的 probe/baking，以及长时间工程性能评估。

### Phase 6：Occlusion / Transmission

当前 Python schema 会显式拒绝非 `none` 的 `occlusion`，这是防止静默降级的有意限制，不代表功能已实现。

- [ ] 木门、实心门、石膏板、混凝土墙和楼板的遮挡状态。
- [ ] 3-band transmission 与材质导致的高/中/低频变化。
- [ ] 声源从遮挡区进入可见区时的平滑过渡。
- [ ] 门后低语、隔墙敲击、楼上拖拽和走廊拐角脚步的专项听感与频谱验收。

### Diffuse / Ambisonics 环境声床

当前 renderer 明确拒绝 `diffuse`，WebUI 首版也不会生成该模式。Ambience 现阶段只能作为点声源或保留立体声处理。

- [ ] 实现 diffuse/Ambisonics 环境声床输入、解码与方位旋转。
- [ ] 验证走廊底噪、风雨、人群等环境声不被压缩成单一明显点声源。
